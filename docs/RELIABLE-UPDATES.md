# Надійне автоматичне оновлення «Наше Світло»

## Зміна інтервалу на 2 хвилини (20.11.26)

**Завдання cron-job.org уже існує:** перевірені GitHub Actions показують зовнішні `workflow_dispatch` приблизно кожні 10 хвилин. **Не створюйте нове** завдання. Увійдіть у [cron-job.org](https://cron-job.org/en/), відкрийте `Dashboard → Nashe Svitlo → Edit` і змініть тільки **Schedule → Every 2 minutes** (хвилини 00, 02, 04, …, 58). Збережіть завдання, не змінюючи URL, заголовків і токена.

- Власний GitHub `schedule` залишається резервним кожні 5 хвилин; GitHub може затримувати або пропускати запуски.
- Сайт перевіряє нові знімки EcoFlow кожні 20 секунд. Новий SOC можливий лише після успішного отримання від EcoFlow й публікації через GitHub Pages.
- Запуски з інтервалом 2 хв збільшують кількість REST API-запитів EcoFlow, тому після перемикання перевіряйте HTTP 429, помилки quota і чергу GitHub Actions; якщо проблеми повторюються, використайте 5 хв.
- Після зміни перевірте у [GitHub Actions](https://github.com/EpicMan1997/nashe-svitlo/actions/workflows/refresh.yml), чи `workflow_dispatch` справді створюються з ~2-хвилинним інтервалом. Загальний час оновлення не гарантується до 2 хв через чергу, запуск та деплой.

Якщо завдання або токен втрачені, нижче залишається інструкція для відновлення.

## 1. Токен GitHub (лише якщо попередній не працює)

У GitHub відкрийте Settings → Developer settings → Personal access tokens → Fine-grained tokens → Generate new token.

- Resource owner: **EpicMan1997**
- Repository access: **Only select repositories** → **nashe-svitlo**
- Repository permissions: **Actions → Read and write**. Інші дозволи залишіть мінімальними; GitHub додає базовий доступ до метаданих автоматично.
- Expiration: виберіть термін із запасом (наприклад 90 днів) і налаштуйте нагадування для поновлення.

**Не розміщуйте токен у файлах репозиторію, адресі URL або чатах.** Збережіть його лише в приватному заголовку завдання cron-job.org. Сервіс зможе запускати GitHub workflow від вашого імені, тому довіряйте йому як зовнішньому оператору секрету.

## 2. Налаштування наявного cron-job.org job

У [cron-job.org](https://cron-job.org/EN/) → відкрийте існуюче завдання та **Edit** (створюйте нове лише за відсутності старого):

- Title: \`Nashe Svitlo — refresh GitHub\`
- URL: \`https://api.github.com/repos/EpicMan1997/nashe-svitlo/actions/workflows/refresh.yml/dispatches\`
- Request method: \`POST\`
- Schedule: **Every 2 minutes** (хвилини 00, 02, 04, …, 58 кожної години)ntent: \`{"ref":"main"}\`
- Header \`Authorization\`: \`Bearer <YOUR_FINE_GRAINED_TOKEN>\`
- Header \`Accept\`: \`application/vnd.github+json\`
- Header \`Content-Type\`: \`application/json\`
- Header \`X-GitHub-Api-Version\`: \`2026-03-10\` (опціонально)

Не передавайте токен через URL, query-параметр або тіло запиту. Використовуйте лише HTTPS. Увімкніть email-сповіщення про **failed runs** та **recovered** у cron-job.org.

GitHub REST API наразі може повернути HTTP **200** із даними запуску; для деяких версій API — **204 No Content**. Обидва коди можуть означати прийнятий запит. \`401\` / \`403\` — помилка прав або токена; \`404\` — хибний шлях або відсутність доступу; \`422\` — некоректне тіло/гілка.

## 3. Обов'язково перевірити результат

1. Натисніть **Test run** у cron-job.org.
2. Відкрийте [GitHub Actions](https://github.com/EpicMan1997/nashe-svitlo/actions/workflows/refresh.yml).
3. Має з'явитися новий запуск із типом **workflow_dispatch**.
4. Після успішного завершення відкрийте [Наше Світло](https://epicman1997.github.io/nashe-svitlo/): у блоці «Інтервали та джерела» час «Перевірено» повинен змінитися.
5. За 10–15 хвилин перевірте, чи отримали **кілька успішних** оновлень із зовнішнього планувальника.

**Резервний GitHub `schedule` кожні 5 хвилин залишаємо увімкненим**. Якщо GitHub накопичує чергу або EcoFlow починає обмежувати запити, зменште частоту зовнішнього завдання до 5 хвилин.

## Чим відрізняються перевірки

- cron-job.org успішно викликає API → GitHub прийняв запит; це **ще не гарантія** завершення workflow і нової публікації.
- GitHub workflow успішно виконав \`scripts/refresh.py\` і Pages deploy → дані **справді опубліковані**.
- Зелений індикатор графіка → кілька джерел погодилися; це **окремий** показник від давності перевірки.
- Кільце давності відлічує час **від фактичного опублікованого запуску**, а не від запланованої події.

Підтримка токена з терміном дії та зовнішнього сервісу потрібна. Повної гарантії жоден безкоштовний планувальник не дає, але цей шлях усуває конкретний механізм втрати GitHub \`schedule\`.
